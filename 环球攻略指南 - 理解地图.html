02 · 零基础背景包

进入原文拆解前，先补读懂本文必须知道的基础概念。

背景补充
1. 什么是 JSON Schema

JSON Schema 是一种用 JSON 格式描述"数据应该长什么样"的规范。它定义了有哪些字段、字段类型是什么、哪些必填、引用关系怎样。类比：它就像数据库的表结构定义（CREATE TABLE），但用 JSON 而非 SQL 写。

为什么读本文需要它：这个项目的核心设计就是用 Schema 同时约束 AI 输出和模板渲染输入。

背景补充
2. 什么是 SPA（单页应用）

SPA = Single Page Application。整个应用只有一个 HTML 页面，用户点击链接时不刷新页面，而是通过 JavaScript 动态切换内容。路由用 URL 的 hash 部分（如 `#attractions/xxx`）来标识当前显示哪个"页面"。

为什么读本文需要它：这个项目的前端是一个 23 路由的 SPA，所有路由都在一个 HTML 文件内。

背景补充
3. 什么是 Jinja2 模板引擎

Jinja2 是 Python 的一个模板库。它让你在 HTML 里写占位符（如 `{{ variable }}`），Python 程序在构建时把真实数据填进去，输出一个完整的 HTML 文件。它在服务端运行时渲染，不是在浏览器里动态渲染。

为什么读本文需要它：这个项目的生成器用 Jinja2 把 JSON 数据注入到 HTML 模板中。

背景补充
4. 什么是双向索引（Back-reference）

在数据系统中，A 引用 B 时，通常只能从 A 找到 B。双向索引是反过来也建立一份映射：从 B 也能找到"谁引用了我"。这需要在构建时额外计算一份反向查找表。

为什么读本文需要它：这个项目用 4 套双向索引让任意两个实体都能建立连接。

事实
原文结构类型：机制型文章

这不是观点论证文，而是系统设计说明。核心结构是"问题→分层方案→每层细节→扩展性"。

第一层：原始素材 → 结构化 Markdown
输入：截图/备忘录/口述（完全非结构化）

输入：16 份 Markdown
约束：JSON Schema（声明实体/字段/引用关系）

↓ Python + Jinja2
第三层：JSON → 双向索引 + 模板注入
输入：14 个 JSON
处理：build_maps() → build_indexes() → 序列化 → Jinja2 render
输出：4 套双向索引 + DATA/INDEXES 全局变量
↓ 一键生成
第四层：单 HTML 离线应用
产物：guide.html (~350KB)
特性：23 路由 SPA、零依赖、100% 离线、微信可发

05 · 核心判断与依据

判断 ①
Schema 是"翻译层"，不是"验证工具"
原文依据："它既是对 AI 输出的约束契约，也是 HTML 模板渲染的数据源。Schema 设计好了，上游 AI 知道该怎么写，下游模板知道该怎么读。"（作品集.md）

为什么重要：大多数项目把 Schema 当成事后校验的工具。这个项目把 Schema 提升为系统的核心接口——AI 和模板都以它为准。改了 Schema，上下游自动适应。

可能的误读：以为 Schema 只是"JSON 格式检查器"。实际上它是整个流水线的契约层。

判断 ②
一切皆 ID 引用，杜绝文本内嵌
原文依据："{ 'id': 'rest_three_broomsticks', 'recommended_dish_ids': ['dish_roast_chicken_ribs', 'dish_butterbeer'] } ——数据只存在一个地方（Single Source of Truth），修改菜品名只需改 dishes.json 一处。"（作品集.md）

为什么重要：文本内嵌是数据系统中最常见的技术债。一旦菜品名改了，所有引用它的地方都要同步改。ID 引用让修改变成单点操作，而且让双向索引成为可能。

类型：这是作者明确表述的设计判断，不是推论。

判断 ③
单 HTML + 零框架，不是偷懒，是刻意选型
原文依据："数据量小（350KB），引入 React/Vue 反而增加体积和复杂度。Vanilla JS + Jinja2 模板足以支撑 23 个路由的 SPA，且产物更小、加载更快。"（design.md）

三个设计约束决定了这个选型：

  • 离线优先：园区内无信号，必须单文件可用
  • 分享门槛低：微信发送一个文件即可，不需要安装
  • 数据量小：350KB 数据不值得引入框架的复杂度
判断 ④
双向索引由 Python 在构建时自动计算，不靠前端硬编码
原文依据："这些关联不是手写硬编码的，是 Python 从 JSON 的 ID 引用关系中自动计算出来的。"（作品集.md）

为什么重要：如果关联关系靠前端 JS 硬编码，每次增删实体都要改 JS。构建时计算意味着前端代码是通用的——换一套数据，同样的代码就能工作。

判断 ⑤
AI 是执行者，人是决策者
原文依据："你是产品经理，AI 是你的全栈工程师。"（docs/usage.md）"不擅自拍板（方案需你确认）"（角色分工表）

为什么重要：这个项目不是"AI 自动做一切"。它设计了清晰的人机分工：AI 负责读写数据、改代码、跑命令；人负责决策、提供素材、审核结果。这比"AI 全自动"更可靠。

判断 ⑥
四组件耦合，改一个必须查其余三个
原文依据："这套系统有 4 个组件通过字段名紧密耦合。改其中一个必须检查其余三个。"（docs/usage.md）——schema.json ↔ data/*.json ↔ schema_generator.py ↔ guide_template.html

为什么重要：这是这套架构的主要代价。Schema 驱动带来了自动化和一致性，但也带来了耦合。作者没有回避这一点，反而在文档中详细列出了 5 种修改场景的联动规则。

06 · 关键概念拆解

概念 ①
Schema 驱动架构

原文怎么用："Schema 驱动架构：schema.json 定义数据结构，generator/schema_generator.py 读取 Schema 生成索引"（workflow.md）

人话解释：先定义"数据应该长什么样"（Schema），再按这个定义去填数据、写代码。Schema 是所有组件共同遵守的契约。

和其他概念的关系：Schema 是四层流水线中第二层的核心。它同时约束上游（AI 输出格式）和下游（模板渲染输入）。

原文依据："修改数据结构只需更新 Schema，验证和生成自动适应。"（README.md）

不要误解成：Schema 只是一个 JSON 文件。它是整个系统的设计哲学——用声明式定义驱动一切。

概念 ②
Single Source of Truth（数据单一来源）

原文怎么用："数据只存在一个地方（Single Source of Truth），修改菜品名只需改 dishes.json 一处。"（作品集.md）

人话解释：每条信息只存一份。所有需要这条信息的地方，都通过 ID 去引用它，而不是复制一份过来。

和其他概念的关系：这是"一切皆 ID 引用"原则的底层逻辑。正因为数据只有一份，ID 引用才有意义。

不要误解成：这意味着数据冗余为零。标签（tags）被多个实体引用，这是引用关系，不是冗余。

概念 ③
四套双向索引

原文怎么用："build_indexes() 返回包含 4 个索引的字典：tag_index、zone_index、backrefs、alternative_index"（workflow.md）

人话解释：

  • tag_index：按标签找实体（"高刺激"标签下有哪些项目？）
  • zone_index：按园区找实体（哈利波特区有哪些餐厅？）
  • backrefs：反向引用（哪些技巧提到了这个项目？）
  • alternative_index：替代关系（这个菜品有哪些替代选项？）

和其他概念的关系：索引的构建依赖 ID 引用关系。没有"一切皆 ID"，就不可能自动计算这些索引。

概念 ④
四组件耦合

原文怎么用："schema.json ↔ data/*.json ↔ schema_generator.py ↔ guide_template.html —— 字段定义必须一致、字段名必须一致、变量名必须一致、校验规则必须匹配"（docs/usage.md）

人话解释：这四个文件通过字段名"锁"在一起。改了 schema.json 里的字段名，其他三个文件必须同步改，否则系统报错。

和其他概念的关系：这是 Schema 驱动架构的代价。换来的好处是：只要 Schema 对了，上下游自动对齐。

概念 ⑤
构建时 vs 运行时

原文怎么用："Jinja2 在构建时完成模板渲染，运行时零开销。"（design.md）"Python 从 JSON 的 ID 引用关系中自动计算出来的"（作品集.md）

人话解释：所有复杂计算（索引构建、模板渲染、数据注入）都在"构建时"完成——也就是你跑 python 命令的时候。用户打开 HTML 时，一切已经是成品，不需要再计算。

和其他概念的关系：这是"单 HTML + 零框架"选型成立的前提。正因为复杂逻辑在构建时处理完了，运行时只需要简单的 Vanilla JS。

概念 ⑥
联动修改规则

原文怎么用："场景 A：只换数据不改结构 —— 只改 data/ 下的文件。场景 B：去掉某些实体类型 —— 需要同步改 4 个地方。"（docs/usage.md）

人话解释：作者把修改操作分成了 5 种场景（A-E），每种场景列出了具体要改哪些文件。这是一份"操作手册"，防止改了 A 忘了 B。

09 · 误解与边界

误解 ①
"Schema 只是验证工具"

可能误解：以为 schema.json 只是用来检查 JSON 格式对不对的。

原文真正说了什么："它既是对 AI 输出的约束契约，也是 HTML 模板渲染的数据源。"——它是接口，不是守卫。

原文没有说什么：没有说 Schema 可以替代 API 设计或数据库设计。

如何避免：记住 Schema 在这个项目中是"翻译层"，同时服务上游和下游。

误解 ②
"单 HTML 是技术限制"

可能误解：以为选单 HTML 是因为作者不会用框架，或者是项目太小不值得用。

原文真正说了什么："园区内无网络是核心痛点，单文件方案彻底消除网络依赖。"——这是刻意的设计决策，不是能力限制。

如何避免：从用户场景（无信号+微信分享）倒推技术选型，而不是从技术能力出发。

误解 ③
"AI 自动完成一切"

可能误解：以为用户只需要丢素材进去，AI 就能自动生成完美攻略。

原文真正说了什么："你是产品经理，AI 是你的全栈工程师。"——需要人确认方案、审核结果、提供决策。AI 不擅自拍板。

如何避免：注意 usage.md 中的 Phase 1（确认需求）明确要求"等待用户确认再动手"。

误解 ④
"这套架构只适用于主题公园"

可能误解：以为这是一个环球影城专属工具。

原文真正说了什么："这套数据结构和页面模板其实不限于环球影城——换一套数据，上海迪士尼、成都美食地图、甚至个人影单推荐都能用。"（README.md）

如何避免：理解 Schema 是通用的，数据是可替换的。

10 · 背景知识缺口

要完全理解这篇，还需要补哪些背景

🔑 推荐补（直接影响理解深度）：

  • JSON Schema 规范——理解 $schema、type、ref、required 等关键字的含义。建议先看 json-schema.org 的 5 分钟入门。
  • 数据归一化理论——"一切皆 ID 引用"本质上是数据库设计中的第三范式（3NF）。了解 1NF/2NF/3NF 能帮你理解为什么要消除文本内嵌。

📌 可以先不补（了解即可）：

  • Jinja2 模板语法细节——知道"构建时渲染"就够了，不需要会写模板。
  • Vanilla JS SPA 路由实现——知道用 hash 路由就够了，不需要会手写路由库。
  • GitHub Actions CI/CD——和架构设计无关，只是部署方式。

🎯 推荐下一步学习问题：
